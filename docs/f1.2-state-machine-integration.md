# F1.2 — Integración de la máquina de estados

## Alcance implementado

La máquina definida en F1.1 es ahora la única autoridad para el estado de la experiencia del workspace. Zustand conserva el estado resultante y `AgentSessionProvider` emite eventos; ningún componente asigna estados directamente.

No se modificaron el backend ni los contratos comunes. Los estados de pago quedaron preparados en la máquina, pero no se activan desde eventos genéricos: sólo podrán conectarse cuando el contrato compartido exponga eventos explícitos de confirmación y ejecución.

## Mapeo del runtime

| Señal del frontend o stream | Evento de experiencia |
| --- | --- |
| Envío de prompt | `SUBMIT` |
| Solicitud de datos | `DATA_REQUESTED` |
| Inicio de UI progresiva | `UI_GENERATION_STARTED` |
| Interacción sobre una UI vigente | `UI_UPDATE_STARTED` |
| UI completa y revisión válida | `UI_COMMITTED` |
| Conflicto de revisión | `REVISION_CONFLICT` y resultado `partial` recuperable |
| Error clasificado | `FAIL` con ámbito de conversación, UI, datos o pago |
| Cancelación del usuario | `CANCEL` con ámbito de generación |
| Selección de un snapshot | `RESTORE_SESSION` |
| Nueva consulta limpia | `RESET` |

Las etapas `connecting` y `thinking` que llegan por AI SDK o por el stream permanecen como detalles de transporte. Ya no son estados públicos del workspace.

## Reglas preservadas

1. Si existe `hasValidSnapshot`, una nueva generación se considera `updating` y mantiene visible la UI estable.
2. Recibir nuevamente el mismo `sessionId` no reinicializa las revisiones de UI y datos.
3. Una cancelación o error conserva el snapshot válido.
4. Un error de UI o datos no cambia el dominio de pagos.
5. Un pago en ejecución no acepta una cancelación tardía.
6. Las transiciones no permitidas se rechazan sin mutar el estado.

## Pendiente para el siguiente subpaso

La restauración después de recargar todavía no está implementada. Los snapshots continúan en memoria; persistencia y rehidratación corresponden al siguiente trabajo de F1.
